# vermix-kpp-doublediff

Upstream test: `code/mitgcm/verification/vermix/input.dd`. Policy: `pointwise`.

## The test

KPP double-diffusive mixing in an unforced column. `run.sh` builds one MITgcm executable for this
configuration with the tree's own `tools/genmake2` (the build configuration
under `mods/`: `SIZE.h`, `packages.conf` and the option headers of the
upstream experiment, gfortran optfile `linux_amd64_gfortran`, one process,
tiles only), then runs it on the deck under `ic/<ic>/`. Configuration:
verification/vermix with the input.dd overlay: the same single 1x1x26 water column on a 5 km Cartesian footprint (one tile, DISCONNECTED_TILES) but on a slightly different vertical grid (26 levels from 10 m to 46 m), with a linear equation of state (tAlpha=2e-4, sBeta=7e-4) instead of MDJWF, no surface forcing at all (the overlay's data has no PARM05 forcing entries and no periodicExternalForcing, so Qnet_72.forcing and taux_72.forcing are simply not read) and no background vertical diffusivity (diffKzT and diffKzS are commented out), started from the T.doublediff and S.doublediff profiles that the experiment was built around: in the upper eight interfaces warm salty water sits over cold fresh water at a density ratio of exactly 1.1, the salt-finger regime, in interfaces 9 to 22 the salinity gradient wins and the column is statically unstable, and in the bottom four interfaces cold fresh sits over warm salty at a ratio of 0.5, the diffusive-convection regime; the only mixing is what pkg/kpp returns, with KPPuseDoubleDiff=.TRUE. and the package defaults Ricr=0.3, Rrho0=1.9 and dsfmax=1e-2, and with EXCLUDE_KPP_DOUBLEDIFF left undefined in the experiment's KPP_OPTIONS.h so the double-diffusion routine is compiled in; the window is deliberately shorter than the five days of the other vermix checks, 120 steps of 1200 s or forty hours, six times the upstream twenty-step window, because the statically unstable middle of the column is being convectively homogenised and a longer window would drive those interfaces towards the density ratio of one where the salt-finger branch switches on..

The production path it forces: pkg/kpp/kpp_calc.F driving KPPMIX, BLDEPTH, RI_IWMIX, BLMIX and ENHANCE in pkg/kpp/kpp_routines.F, and in this deck additionally the KPP_DOUBLEDIFF routine at the end of pkg/kpp/kpp_routines.F, which forms the density ratio from alphaDT and betaDS and adds the salt-finger and diffusive-convection diffusivities to kappaRT and kappaRS; the profiles are handed on by pkg/kpp/kpp_calc_visc.F, kpp_calc_diff_t.F and kpp_calc_diff_s.F and applied by the tridiagonal solves in model/src/impldiff.F and model/src/solve_tridiagonal.F, with the linear equation of state evaluated in model/src/find_rho.F every step..

Runtime knobs (`run.sh --help`): `SAB_STEPS` (default 120, the graded
value; the upstream deck runs 20 steps of 1200 s) scales the
run linearly, and `SAB_BUILD_JOBS` (default 4) only the build. Expected run
time on the declared resources, build excluded: about 3 s;
the per-check build (roughly 40 s on an x86_64 host) is reported by `run.sh`
as `SAB_BUILD_SECONDS` and does not count against the suite budget.

## The two initial conditions

`ic/nominal` is the upstream deck, assembled as `testreport` assembles it
(the experiment's `input/`, the input.dd/ overlay),
with these deck edits: `nTimeSteps` set to the graded window, `dumpFreq`,
`pChkptFreq` and `chkptFreq` set to zero and `dumpInitAndLast=.TRUE.` so that the only
state written is the initial and final dump, and
`writeBinaryPrec=64` so the dump is double precision and `useSingleCpuIO=.TRUE.` so the dump is one global file per field rather than one per tile; `useMNC=.FALSE.` in `data.pkg`; `kpp_dumpFreq=144000.` in `data.kpp`; `useSingleCpuIO=.TRUE.` in `data`.

`ic/variant` holds only the deck files that differ, laid over `ic/nominal` by
`run.sh`; the difference is `dsfmax=0.010000000000000004` in `data.kpp` instead of 0.01:
two ulps of the graded precision (binary64) on a parameter that enters the
tendency from the first step, a distinct double, so the two runs differ at
round-off level from the first step. The
spread between them is the check's measured sensitivity under the pass policy
and must stay inside the bound.

`run.sh altbuild` runs `ic/nominal` on an alternative build of the same source, `genmake2 -ieee` (gfortran -O0
-ffloat-store, strict IEEE arithmetic) instead of the optimised optfile; grading never uses it, self-validation measures the
check's floor between two legitimate builds from it.

## The pass policy

Every cell of every prognostic field in the final state dump must satisfy
|candidate - reference| <= 1e-10 + 1e-08 |reference|.
The relative part is the working bound because the fields span many orders of
magnitude; the absolute part covers cells at or near zero. The observable is every cell of the final prognostic dump plus the instantaneous KPP viscosity, diffusivity, non-local flux and boundary-layer depth that the kpp_dumpFreq edit makes pkg/kpp/kpp_output.F write at the final iteration, compared relatively with an absolute floor. The bound is physical because the double-diffusive diffusivities are a closed algebraic function of the local density ratio with no iteration and no tuning inside the step, so each of the faults above displaces the graded profiles by parts in a hundred or worse, six orders of magnitude above the round-off floor. It is achievable for the same reason as the other vermix checks: the domain is one disconnected column, there is no horizontal exchange and no global reduction, the barotropic solve is degenerate on a single point and the upstream log for this deck records cg2d_init_res as exactly zero at every step, and everything downstream is a direct tridiagonal factorisation with no convergence test, so two runs of the same build are bit-identical and the whole measured spread is the amplification of the deliberate two-ulp change to dsfmax. The one thing a reviewer must understand is why the window is forty hours rather than the five days used for the other vermix decks. KPP_DOUBLEDIFF selects between three branches on strict inequalities, and the finger branch is not continuous at its boundary: at a density ratio just above one the salt diffusivity is the full dsfmax, and just below one it is zero, so an interface sitting exactly at Rrho = 1 could flip under a two-ulp perturbation and change that interface's salt diffusivity by 1e-2 m2/s. At the initial state no interface is anywhere near that boundary, because the experiment was built with density ratios of exactly 1.1, 0.5 and 0.5, a ten percent margin that is fourteen orders of magnitude wider than the perturbation. What erodes the margin is time: interfaces 9 to 22 start statically unstable, KPP mixes them convectively at difmcon = 0.1 m2/s, and as they approach neutrality their density ratio approaches one. The homogenisation timescale of that 200 m thick layer at 0.1 m2/s is about four days, so forty hours leaves the margin largely intact while five days would not. If a native window scan at 20, 60, 120, 240 and 360 steps shows the worst relative spread growing smoothly, the window can be lengthened to 360 to match the rest of the vermix family; if it shows isolated interfaces with O(1) differences instead, that is the finger branch flipping and the window must be shortened further, not the bound loosened.
Faults: This is the only check in the suite in which temperature and salinity are given different vertical diffusivities by design, so a fault in that asymmetry is directly visible. Dropping the factor 0.7 that ties the finger-regime heat diffusivity to the salt diffusivity (nuddt = 0.7*nudds in KPP_DOUBLEDIFF) makes the two tracers diffuse at the same rate and destroys the density-ratio evolution: the temperature and salinity profiles differ by hundredths of a kelvin and thousandths of a practical salinity unit within a day, parts in 1e-3 of both fields. A wrong exponent in the cubic (1-(Rrho-1)/(Rrho0-1))**3 of pkg/kpp/kpp_routines.F changes the finger diffusivity by tens of percent at Rrho=1.1, which the graded KPPdiffKzS snapshot shows at parts in 1e-1. Omitting the diffusive-convection branch (Large et al. 1994 equations 32 and 34) leaves the bottom four interfaces mixing at the molecular rate only, an O(1) change in KPPdiffKzT there. Mis-ordering the strict comparison alphaDT > betaDS > 0 swaps the two regimes and gives an O(1) error over most of the column. Single-precision double-diffusion arithmetic leaves relative errors near 1e-7 in the salinity profile.

## Evidence

The overlay supplies only data and data.kpp; data.pkg, data.diagnostics, data.mnc, eedata and the initial and forcing binaries come from input/. data.pkg therefore still sets useMNC=.TRUE. and must be turned off (no NetCDF in the image). Because the overlay's data has no forcing entries, Qnet_72.forcing and taux_72.forcing are present but unread; they are deliberately not dropped so that the deck stays recognisable and so that a reviewer restoring the forcing lines does not have to hunt for them. T_26.init is likewise unread (hydrogThetaFile is T.doublediff) and kept for the same reason. kpp_dumpFreq is set to 144000., which is steps*dt, because the generator's dumpFreq=0 otherwise suppresses the KPP snapshot: pkg/kpp/kpp_output.F gates on DIFFERENT_MULTIPLE(kpp_dumpFreq,...) and that function returns false for a zero frequency; if an operator overrides SAB_STEPS the snapshot simply disappears from both runs, which is harmless. The deck inherits input/data.diagnostics, whose four streams all have a frequency of 432000 s, that is 360 steps, so none of them fires inside this 120-step window and only the core state dump and the KPP snapshot are graded; that is why this check needs no not_graded entry for DFrI_TH, unlike vermix-kpp. All input binaries are real*8 and the deck sets readBinaryPrec=64. ivdc_kappa is commented out, so model/src/calc_ivdc.F never runs and KPP is the only mixing path. This deck sets neither globalFiles nor useSingleCpuIO, so MITgcm's mdsio writes one file per tile and names the final dump <field>.<iteration>.001.001.data (pkg/mdsio/mdsio_write_field.F, the 'Case of 1 file per tile' branch), which the generator's collector and validate.py, both of which match ^<field>.<10 digits>.data$, would not see at all; the extra edit useSingleCpuIO=.TRUE. makes mdsio gather the tiles and write one global file per field, exactly as every sea-ice check's deck does. It is a pure I/O switch and changes no arithmetic; globalFiles=.TRUE. would do the same job for the non-exch2 decks, but useSingleCpuIO is the variant the finished task already exercises.

Floor: self-validation measures it on every run from `run.sh altbuild`, the same source under genmake2 -ieee, graded against the nominal run with this check's validate.py, and records it in the rubric's evidence (floor, altbuild); that in-image number is the floor a reviewer reads. The native measurement of 2026-09-02 between the same two builds on the x86_64 host: the optimised gfortran build and the IEEE -O0 build differ on this deck by at most 0.0e+00 in absolute terms, 0.0e+00 of the bound (in no field); the two builds pass each other under the rule. Faults, same build with one parameter changed: the cg2d target residual loosened to 1e-3 uses 0.0e+00 of the bound (NO EFFECT: one water column, 1x1 horizontally, so the surface-pressure solve has nothing to iterate and its target cannot change the result), and the variant parameter off by five percent 3.9e+02 of the bound (FAIL). Measured run time of the nominal deck, build excluded: 0.1 s natively.
